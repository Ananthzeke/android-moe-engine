# Unit 2: per-request measurement on the phone

Measured on the physical vivo 1920 (Snapdragon 665, 8 GB RAM, Android 12) with the Unit 2
server (`ame-server`, SHA-256 `c9ca9704008844a143eb65cbc980559c49675050101cad1f0be75d264e4e67e8`,
built against the rebuilt, patched llama.cpp `ff5a233`). The enrolled Qwen3.6-35B-A3B Q4_K_M
artifact ran with 64 slots, a 256 MiB arena allowance, context 512, 4 threads, port 8081,
greedy sampling. Charger connected, battery 46-47%, battery temperature 30.3-33.2 C. Scope
of every number: one process, one series, uncontrolled OS page cache (about 5.4 GB cached at
the start), no other inference server running during the series. A stale older server (the
previous playground session) was still running for the first minutes of startup and was killed
by PID before the series; `deploy/phone/stop.sh` had missed it because it matched an absolute
path. Raw files: `health-ready.json` (startup record), `series/` (every request, response and
`/health` before and after), `requests.jsonl` (the server's own log), `summary.md` (generated by
`tools/summarize_series.py`), and the phone state snapshots.

Commands:

```sh
AME_REQUEST_LOG=/data/local/tmp/ame-api/unit2-requests.jsonl ./start-35b.sh   # on the phone
.venv/bin/python tools/request_series.py --output-dir series --label unit2 --short 3 --long 1
.venv/bin/python tools/summarize_series.py series --health health-ready.json
```

## Where startup time goes

One clean restart took **170.6 s** to ready. **168.7 s of it (99%) is the SHA-256 of the
artifact inside `artifact_open`**, during which the process read 20.43 GB through read calls
(`rchar`) and the block layer reported 19.92 GB (`read_bytes`), about 119 MB/s of application
reads. Manifest validation took 0.043 s, model load 1.54 s, contract binding 0.05 s,
template initialization 0.02 s. Model load issued 11 MB of read calls and 6 major faults.

The historical 1,732 s to ready (`evidence/api/phone-35b-direct/run.json`) was **not
reproduced** and cannot be decomposed: that run had no stage records, and its boundary was
"monitor start", not "process start". Plausible but unmeasured contributors are a cold page
cache for the 20 GB hash, a second hash or process running concurrently, and time before the
process started. The next startup anomaly will show up as one stage's seconds or its
`read_bytes` growing; the stage records are now in `/health` and in the request log.

## Where per-request time goes

All four requests completed with status `completed`. Short request: 24 prompt tokens, three
sampled tokens, two decode steps.

| Request | Total s | Prefill s (read s inside) | Decode s (read s inside) | Prefill expert bytes | Decode expert bytes |
| --- | ---: | ---: | ---: | ---: | ---: |
| short 1 | 58.4 | 52.69 (40.23) | 5.58 (4.06) | 6.61 GB | 1.13 GB |
| short 2 | 50.1 | 44.98 (35.92) | 4.97 (3.57) | 6.61 GB | 1.13 GB |
| short 3 | 50.8 | 45.35 (36.63) | 5.29 (3.53) | 6.61 GB | 1.13 GB |
| long (32 tokens) | 114.6 | 56.01 (44.03) | 58.38 (41.36) | 8.17 GB | 17.55 GB |

- **Both phases are dominated by serial expert reads.** `read_seconds` is the wall time
  inside the file source (page-cache copies included, not flash time). It is 76-81% of
  prefill and 71-73% of decode. The remainder, 8.7-12.5 s of prefill and about 0.55 s per
  decode token in the long request, is compute, barrier waits, and sampling together.
- **Short requests are prefill-bound.** Prefill is 90% of a 24-token request. Each 8-token
  prefill unit reads about 31 distinct experts per routed tensor (11,205 slices over three
  units), so prefill moved 6.6 GB for 24 tokens, about 275 MB per prompt token against
  566 MB per decode token.
- **Decode reads are exactly the working set**: 960 slices (566 MB) per token, zero cache
  hits, one `pread` per slice. The long request decoded 31 steps at a median 1.70 s
  (range 1.26-2.94 s), 0.53 tokens/s over the decode phase.
- **Physical reads exceeded requested reads during prefill.** Block-layer `read_bytes` was
  1.9-2.75x `rchar` in prefill (12.7-18.2 GB against 6.6 GB) and 0.6-1.1x in decode, where
  the page cache served part of the repeat pattern. These counters have different scopes and
  their ratio is not a hit rate. The excess in prefill is consistent with readahead around
  each 576 KiB read, but this run does not isolate the cause. Major faults in prefill were
  1,431-3,085 and system-wide `pswpin` 13,021-41,421 pages (53-170 MB); decode was lower.
- **No throttling was visible.** The big cores (cpu4-7, found from `cpuinfo_max_freq` =
  2,016,000 kHz; cpu0-3 top out at 1,804,800) read 2,016,000 kHz at every boundary except
  the idle `context_create` start. Two instants per phase cannot show a drop inside a phase.
- **Memory.** Process peak RSS 2,134,712 kB (`VmHWM`), RSS 1,998,076 kB, `MemAvailable`
  stayed near 5.7-5.8 GB. Arena 37,748,736 bytes. Not a process cap.

## What this decides

The time is storage reads on the generation thread in both phases, not a hidden fault or
swap storm: Unit 4 (one cache owner, no second page-cache copy) and the read-overlap units
that follow it address the measured cost, and the plan order stands. One caution carries into
Unit 4: prefill reads scale with the number of units, and the unit size is `slots / top-k`.
A per-layer pool that is much smaller than 64 slots would shrink the prefill unit and raise
prefill read volume; the pool size must be chosen with prefill in the replay and on the phone.

## Limits

One series, one prompt pair, uncontrolled page-cache state, no thermal history, no per-token
frequency. `read_seconds` is application wall time. Real-35B reference parity is still open.
