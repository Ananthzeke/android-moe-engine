# Expert streaming research for the existing CPU engine

Research synthesis, 20 October 2026

## What this review establishes

The research supports a narrow conclusion. Exact expert streaming is a real systems design, not a speculative idea: BigMoeOnEdge implements it over GGUF and llama.cpp, and Routide implements demand loading, leases, eviction, and optional prefetch over MLX. Neither repository establishes that the existing engine can be made fast or hard-capped by changing a launcher flag. The recorded CPU path has served the exact Qwen3.6-35B-A3B Q4_K_M artifact on the target phone, but it lacks full-model parity against a fully resident reference and does not yet show that expert bytes, staging, backend memory, state, and cancellation all fit a strict accounted limit.

The most useful research transfer is therefore a sequence of bounded experiments around the engine already in use: preserve its backend, native routing, tokenizer, attention, recurrent state, and quantized kernels; measure the request stages correctly; compare the compact arena with a canonical-address streaming design; improve read scheduling only when traces and controlled runs justify it; and treat overlap, reuse, and speculation as separate additions with their own lifetime and correctness gates. No reviewed external result supplies a defensible tokens-per-second forecast for this phone.

This report reviews targeted source and paper sections. It is not a full line-by-line audit of each upstream repository, a reproduction of any paper, a new device benchmark, or proof for source files that were inaccessible or unread. The exact counts and coverage boundaries appear in [research/sources.json](research/sources.json). The report uses original summaries and concise code citations rather than reproducing paper text.

## Target, terms, and correctness boundary

The local target identity comes from `configs/device-vivo-s1-pro.json` and `evidence/phase0/probe-vivo-1920.json`: vivo1920 / S1 Pro, Snapdragon 665 (SM6125), Android 12, API 31, kernel 4.14.180-perf+, 8 GB class memory, and 4096-byte pages. The CPU feature probe reports `fp`, `asimd`, `aes`, `pmull`, `sha1`, `sha2`, `crc32`, and `cpuid`. It does not report dot-product or i8mm. The SHA2 result justifies testing a runtime-dispatched ARM SHA2 implementation against the current scalar hash. It does not establish support for HMX, modern Hexagon features, SME2, or recent ARM matrix instructions. The project instructions prohibit root, bootloader, ROM, or thermal-protection changes, and none are needed for this investigation.

The artifact is `Qwen3.6-35B-A3B-Q4_K_M.gguf`, 20,419,565,568 bytes, SHA256 `671e47e0ec53c665d048b98c3ecbfd5236b5ca9c3e02ed19fc8f81f7b85140c7`, architecture `qwen35moe`, 40 layers, 256 experts, top 8. It is not interchangeable with Qwen3-30B-A3B, Mixtral, a MobileMoE checkpoint, an MLX affine-INT4 pack, or an expert-pruned model. "35B" is total model identity; active parameter count is not a resident-memory estimate.

This review uses three different claims of exactness. **Storage exactness** means that every selected native expert is materialized from the target artifact without changing its stored quantized bytes. **Greedy sequence parity** means that the implementation emits the same token IDs as an identified reference under the same prompt and settings. **Distributional equivalence** means that a sampling or speculative algorithm preserves the target distribution, including its acceptance/rejection math and state rollback. Passing one does not prove the others. A cache policy can be output-neutral in principle, but only per tested artifact, kernels, shapes, and histories. Prefetch is exact only when the actual router still determines every expert that executes and a miss falls back to demand loading.

For memory, a cache-byte target is not a process cap. A valid hard cap must include page rounding and tail slack, staging and old/new materializations while both are live, metadata, aligned I/O buffers, backend packing and retained weights, contexts, KV and recurrent state, compute buffers, thread stacks, and any shared backing. Report project-owned allocations, RSS, PSS, system memory, application-read bytes, and physical I/O separately. The values have different meanings and time windows. In particular, the author's 4,000 MiB expert payload budget cannot be copied as a target setting on an 8 GB phone: it excludes other live memory and comes from a different device and operating system.

## BigMoeOnEdge: complete expert streaming flow

BigMoeOnEdge is the strongest direct implementation precedent in this source set. Its serial mode reads selected quantized expert slices from GGUF, then binds llama.cpp tensor views to project-owned backing. The backend still computes routing and runs its numerical kernels. The implementation does not transform expert weights into a compact top-k tensor: the kernel continues to address expert `e` at `base + e * nb[2]`. With a cache, each `(layer, projection)` has a full logical virtual reservation and only selected/resident pages are committed. This canonical address model allows demand to arrive in original expert slots and lets existing indexed kernels keep their layout. The shared no-cache buffers are reused across layers; they are not the cache.

The entry point is `Session::Impl` in [session.cpp](https://github.com/Helldez/BigMoeOnEdge/blob/8a2c3f6f4aa8f51737ae62e92de40db386a95e0a/core/src/engine/session.cpp#L751-L864). It requests llama.cpp mmap loading, disables extra/repacked buffers, and configures CPU expert placement. `ExpertLayout` discovers rank-3 expert-indexed tensors and requires a uniform projection suffix set, with no more than three slots. `GgufOffsets` indexes tensor size, type, rows, shard offset and extent without materializing tensors. These checks find a supported arrangement; they are not a complete artifact validator for every quantization block, overflow, file extent, or digest.

A one-token BOS warm-up captures live graph weight objects. The hook records each weight tensor and its `nb[2]` stride. Optional MTP context capture matters because an uncaptured trained head could keep mapped expert views alive. During generation, `RouterHook` exposes the `ffn_moe_topk` graph result. llama.cpp first evaluates and synchronizes that segment. The hook then reads actual token and element strides, collects the selected IDs (a union across prefill tokens), and asks `ExpertStreamSource` to load every unique selected expert. It does not change normal top-k. The serial path drains selected slices before returning from the callback.

With overlap enabled, the source posts projection-major reads and returns. The patched CPU `mul_mat_id` hook waits for the exact expert projection to become ready before consuming it. Previous batches drain before readiness generations and jobs are reused. The backend patch is 34 added lines across `ggml/include/ggml-cpu.h`, `ggml/src/ggml-cpu/ggml-cpu.c`, and `ggml/src/ggml-cpu/ggml-cpu.cpp`, relative to parent `5aeac37a35b44fde4bdffaec9159f2fcb253b622`. It adds one process-global hook and user-data pointer, called before classic and tiled CPU reads. The main repository resolves the setter dynamically. Serial mode can use the public scheduling seam without that hook; overlap requires the fork. The overlap row is therefore not evidence for unmodified-stock execution; its exact historical backend SHA was not bound by the raw record. The claimed stock-compatible serial path was not rebuilt here.

The full source path is distributed across [expert_layout.cpp](https://github.com/Helldez/BigMoeOnEdge/blob/8a2c3f6f4aa8f51737ae62e92de40db386a95e0a/core/src/moe/expert_layout.cpp#L35-L88), [gguf_offsets.cpp](https://github.com/Helldez/BigMoeOnEdge/blob/8a2c3f6f4aa8f51737ae62e92de40db386a95e0a/core/src/moe/gguf_offsets.cpp#L49-L164), [router_hook.cpp](https://github.com/Helldez/BigMoeOnEdge/blob/8a2c3f6f4aa8f51737ae62e92de40db386a95e0a/core/src/moe/router_hook.cpp#L1277-L1460), [expert_stream_source.cpp](https://github.com/Helldez/BigMoeOnEdge/blob/8a2c3f6f4aa8f51737ae62e92de40db386a95e0a/core/src/moe/expert_stream_source.cpp#L35-L303), [FileReader](https://github.com/Helldez/BigMoeOnEdge/blob/8a2c3f6f4aa8f51737ae62e92de40db386a95e0a/core/src/io/file_reader.cpp#L18-L198), and the actual [backend wait hook](https://github.com/Helldez/llama.cpp/blob/efaae99292ee34851137332c6efd20292b5ad4af/ggml/src/ggml-cpu/ggml-cpu.c#L1680-L1700).

`ExpertStreamSource` keeps canonical expert backing, an LRU, file-lane readers, and workers. Direct-I/O windows are rounded outward to alignment and copied from an aligned bounce buffer into exact destination bytes. A direct block is compared with a buffered read at reader open; if they disagree, the reader falls back. That is useful protection against some emulated-storage behavior, not ongoing per-read hashing. Application window bytes, useful expert bytes, and physical device I/O remain separate measurements.

The source preserves model aliases for dense weights by capturing real weight objects and coalescing shared `(shard, offset)` backing. It supports dense anonymous or pinned buffers. Android pinned mode uses CPU-mapped `AHardwareBuffer` BLOBs and falls back per tensor when pinning fails. The code describes a per-allocation cap below 2 GiB and reclaim-exempt allocations, but driver accounting and total phone memory effect are not established for this target. Mapping release is mainly a Windows optimization; the Android control found no read serialization from a live mapping on the tested F2FS phone. It is not a good early Android transfer.

The cache budget is not an end-to-end cap. `entry_bytes` adds logical slice lengths rather than all page-rounded committed bytes or metadata. Miss slices are staged before cold entries are evicted. Current-generation demand can exceed a very small budget. Reservations, adjacent shared pages, tail slack, bounce buffers, dense storage, metadata, compute buffers, KV/recurrent state, stacks, and optional device-prefill arenas all consume memory. Cache auto-sizing samples memory once during source initialization; it does not continuously re-admit as other applications allocate. A zero-available-memory reading is treated as unknown in one branch. A port must refresh telemetry at admission and use explicit reservations for worst simultaneous staging and backend state.

Cancellation propagates through the backend abort callback. Shutdown unregisters the global hook, marks readiness fatal, stops and joins I/O workers, then frees backing and dense buffers. The source assumes no decode is in flight. Removing the hook alone does not drain consumers. Any local equivalent needs consumer counts or another proven drain boundary before it can reuse or release buffers. The global hook also makes concurrent independent overlap sessions unsafe unless ownership is redesigned; BigMoe serializes hosted access through a ticket queue and turn lock.

## Exact and approximate modes in BigMoeOnEdge

| Mode | Numerical status and reason |
|---|---|
| Serial selected-expert streaming with unchanged top-k | Intended output-neutral materialization choice. Uses the same quantized bytes and backend kernels. It still needs artifact-specific parity and complete memory accounting. |
| Cache sizing and buffered versus direct reads | Intended output-neutral residency/I/O choices. Direct-I/O alignment, extra bytes, staging and fallback still need accounting and device tests. |
| Dense `mmap`, `warm`, `anon`, or `ahwb` placement | Intended output-neutral storage choices, with distinct aliasing and memory behavior. `ahwb` has target-specific driver and allocation questions. |
| `--overlap` | Intended output-neutral concurrency mode, but it depends on the small identifiable CPU-backend fork and a readiness/lifetime proof. |
| `--prefetch K`, `--predict-prefetch` | Intended as output-neutral when output-changing cache policies are off. They can waste flash bandwidth, add pollution, and delay demand. |
| `--predict-log` | Diagnostic mode with added GEMVs and barriers. Its timing is instrumented and not a clean baseline. |
| `--n-expert-used k` | Approximate. Overrides model top-k metadata. Excluded from exact comparisons. |
| `--drop-cold-experts`, `--drop-in-prefill`, renormalization options | Approximate. Zero selected weights and redirect IDs to loaded experts; survivors may be renormalized. Excluded. |
| `--expert-substitute L` | Approximate. Boosts cached expert scores and rewrites selected IDs. Excluded. |
| `--route-ahead N` | Approximate. Commits stale-hidden-state predicted IDs as future demand. Excluded. |
| MTP or n-gram decoding | Separate proposal algorithms with their own state and target-verification contracts. Not part of an expert-streaming result. |

The modes are not interchangeable merely because they share code. Expert dropping can make cache size, prefetch and worker timing affect which weights execute, so those settings become output-affecting when dropping is enabled. Route-ahead also differs from speculative prefetch: it rewrites IDs before loading rather than merely issuing a cancellable hint.

BigMoe's numerical gates also need their full scope retained. G1-G7 compare generated-text bytes from short greedy runs. G16c and G17e compare aggregate NLL and top-1 counts at 17-digit formatting precision for device-prefill and streamed-arena paths. G18 compares selected-choice log probabilities; one changed-batch comparison permits relative tolerance 1e-9. These are useful numerical checks, beyond text alone, but are not a retained full-logit/token-ID trace for every architecture. Hook-dependent overlap tests can skip if the hook is absent; `--require-hook` turns that absence into failure. The tests were inspected, not executed here. [Numerical and hook gates](https://github.com/Helldez/BigMoeOnEdge/blob/8a2c3f6f4aa8f51737ae62e92de40db386a95e0a/tests/moe_gates.cpp#L1028-L1044), [streamed NLL gate](https://github.com/Helldez/BigMoeOnEdge/blob/8a2c3f6f4aa8f51737ae62e92de40db386a95e0a/tests/moe_gates.cpp#L1168-L1177), [choice-logp comparisons](https://github.com/Helldez/BigMoeOnEdge/blob/8a2c3f6f4aa8f51737ae62e92de40db386a95e0a/tests/moe_gates.cpp#L1275-L1315).

## Planner, row streaming, and decode proposals

BigMoe's hardware planner separates observation from policy. `probe_and_plan()` registers backends, gathers hardware and model facts, measures device costs and optionally storage, probes headroom and placement, then calls a rule layer to produce a proposed `RunConfig`. Hardware memory is sampled early and not refreshed immediately before the plan is applied. Device isolation is conditional on runner arguments. "Plan" means a recommendation based on observed facts, not a runtime reservation or continuous admission controller.

`probe_headroom()` may increase the apparent available budget from compression accounting. Its explicit active probe reserves and touches at most 24 chunks, samples whether the oldest remains resident, stops at first loss, then releases the memory. It only raises the budget. `probe_placement()` asks backend fitting code for a context/compute projection at one width and half-width, then estimates slopes. `choose_graph_width()` may reduce ubatch to fit a policy share. That is a capacity estimate, not a measured latency optimum. Lowering ubatch is a strong exact candidate because it can free compute reservation for weights, but actual graph peaks and parity must be measured on the target architecture.

`allocate()` ranks dense read-whole groups and fractional expert-cache budget by estimated seconds saved per RAM byte. Cache benefit assumes a linear hit fraction, then scales it by a policy optimism factor above a model token-cycle floor. Missing rates do not imply free execution. Residual budget has an unpriced fallback. The synthetic compute bandwidth probe runs quantized matmuls, warms first, synchronizes, and divides effective work bytes by elapsed time. It is not physical DRAM bandwidth and does not include attention, recurrent updates, router, storage, or tokenization. A quoted planner cost must remain labeled a model estimate.

The optional `RowStream` keeps canonical sparse backing for graph-proven row-only tables. It uses a separate bounded slab window and metadata per table. Tied embedding/output heads are excluded from row-only planning. A non-gather consumer can force whole-table materialization, which then remains non-evictable. The window rounds up to a slab and protects all slabs needed by a current gather, so prefill can exceed its nominal size. That is a soft bound unless admission reserves worst-case gather and fallback or rejects unsupported graphs. Do not infer a hard-cap design from its name.

`ngram_draft()` searches recent token history for the longest suffix match, preferring the most recent equal-length match, then proposes the continuation. It needs no draft weights, but the history scan costs CPU. MTP instead opens a second context over the model, requires a trained `nextn` block, and captures a separate draft graph. Shared model weights do not eliminate extra context, logits, batches, recurrent rollback snapshots, or expert reads. Both proposal sources feed the same target verification loop. The target evaluates `[confirmed token, drafts...]`; only the consecutive draft prefix matching target argmax is accepted. MTP first rewinds its own guessed positions, then catches up over confirmed tokens. A rewind failure is a run failure. Wide-batch arithmetic can differ from serial near ties, so greedy verification does not prove serial token identity in all cases and does not prove sampling distribution equivalence.

Metrics charge draft and catch-up separately; the full verify work is attributed to the first emitted token in a group. Zero-cost rows for later accepted tokens are accounting attribution, not free work. A useful speculative experiment must include proposal overhead, rejected work, full target time, expert union bytes, accepted tokens per target invocation, and exact output checks.

The chat prefix path matches retained token IDs and preserves at least one prompt token for decode. If partial target removal fails, it clears target state and forces full prefill. MTP is rewound separately; cancellation restores pre-turn target and draft state, and final trimming removes decoded but un-emitted positions. These source paths are not fault-injection evidence for every recurrent/SWA model. A separate serialized prefix cache stores one full sequence state and its token prefix, restoring only an exact prefix. It builds a replacement byte vector before discarding the old one, so both buffers can coexist. Prefix snapshots are not the KV allocation itself; serialization time and peak copy memory need separate accounting.

## What the papers establish, and where they stop

### EdgeMoE and mllm

EdgeMoE keeps non-expert parameters resident, keeps expert weights in external storage, and uses a persistent expert cache plus a per-request working buffer. Its offline expert-specific INT2/4/8 channel quantization shrinks storage but then decompresses for computation. Its paper prototype converts to FP32. Thus stored bytes do not determine peak materialized bytes. The paper predicts future expert identities from the preceding two MoE layers and preloads them while compute runs. A miss falls back to the actual router's expert. Prediction schedules I/O; it need not change expert selection. Its stated optimizations do not cover multi-token prefill and multiple requests.

The archived mllm `v1` source at `013e4cecf183358ce5fe5e6a19bee332c50d880c` contains actual MiniCPM expert loading, eviction and prediction code. In `MiniCPMMoE::Forward`, the implementation routes with gate, softmax, top-k, normalization and grouping. For exactly two selected experts it uses the current layer's pair to look up a next-layer prediction, assumes 40-layer wrapping, chooses `c[0]`, waits for preload, then loads any missing actual expert before `moe_infer`. The settings default to four experts per layer and remove the first cached expert not in the needed set. Those are not the paper's global frequency/distance formula. The preload maps and request payload are globals, not a general lease interface. The ARM Linux worker pins to CPU 6, which cannot be transplanted to this device. Selected experts execute and scatter-add normally; they are not skipped.

In that v1 source, `Layer::load/free` dispatches operators. `CPULinear::load` allocates or packs according to the stored dtype; `free` drops the weight. `ParamLoader` can use mmap aliases or seek/read. Dropping a tensor reference does not prove shared mapped backing is gone. Its inspected ordinary read path does not check `fread`'s result, so it is not an appropriate validated materializer template. Current mllm at `1d3c3d8e506e3d12e902af82866972623b240ce0` has a Qwen3 MoE router and grouped expert execution, but no explicit expert-store controller in the inspected body. Neither a Qwen3 example nor that current source proves Qwen3.6 recurrent support or bounded streaming.

The current mllm tree is MIT overall and identifies an Apache-2.0 `wenet` component. Its QNN backend loads runtime libraries and operators, finalizes named graphs, releases cached tensor wrappers, and preserves application input/output wrappers. Releasing wrappers is not proof that compiled static weights stopped occupying backend memory. Setup calls for QNN Linux 2.34+, Hexagon SDK 6.x, Android NDK and CPU plus HTP packages; examples target HVX v75 and README artifacts include SM8650. No Snapdragon 665 path is established. The archived v1 and current main are distinct implementations; the v2 identity `e0b7464f14391df182660e5bbae0164c9c382eaf` was fetched but not deeply read.

### PowerInfer-2

The paper describes a hybrid NPU/CPU system, not generic exact MoE streaming. Offline profiling over more than ten million Wikipedia/RefinedWeb tokens and device profiling select batch-specific hot neurons for dense NPU execution. Decode partitions attention and feed-forward work across CPU/NPU; cold CPU work uses a neuron predictor and a five-stage pipeline for prediction, gate read/compute, and up/down read/compute. Hot-cluster and cold-neuron LRU caches, packed gate/up/down layouts, and 4 KiB staged reads reduce transfer work. The system uses model sparsification and mixed quantization. Small nonzero SiLU values are not exact zeros, and omitted neurons or retrained TurboSparse/Bamboo/ProSparse checkpoints change the model contract.

The reported 11.68 tok/s uses TurboSparse-Mixtral-47B on a rooted OnePlus 12, Snapdragon 8 Gen 3, UFS 4.0, 24 GB physical memory with 19 GB available; all 19 GB are used. It is a hybrid INT4/INT8 system and compares against the authors' LLMFlash and llama.cpp implementations. The paper also reports 2.13 tok/s at a 7 GB budget and itemizes predictor, scales, runtime, non-FFN/KV/head, and cache overhead. The public `Tiiny-AI/PowerInfer` commit `8bd56d69906c9d2dba4d3bf6899763401e01a9a4` redirects from `SJTU-IPADS/PowerInfer` and is MIT. Its README advertises PowerInfer-2, but the inspected source chiefly contains desktop PowerInfer and later SmallThinker. The [author project page](https://powerinfer.ai/) does not establish the missing experiment-to-source mapping. The later `ExpertCache` and `IOUring` code are useful patterns for readiness state, dependencies and aligned I/O, not verified PowerInfer-2 Qualcomm code. Rooting is outside this project's constraints.

### MobileMoE

MobileMoE searches and trains a different model family: 60 routed experts, top 4 and an always-on shared expert, with 1.26/2.82/5.33B total parameters and about 0.3/0.5/0.9B active. It uses sigmoid routing, top-k normalization, FP32 router, balancing losses, group-wise INT4 weights, group 32, and dynamic INT8 activations. Its described custom fused ExecuTorch MoE operator performs token sorting, grouped GEMMs, fused gate/up, SwiGLU, down projection and weighted scatter. The paper says mmap loads activated experts but does not describe a bounded lease protocol. Its memory equation excludes transient activations and runtime overhead.

The authors report 138.1 versus 61.3 tok/s for MobileMoE-S against a separately trained dense MobileLLM-Pro on a Galaxy S25 / Snapdragon 8 Elite. This is a comparison of different models, not a streaming speedup for Qwen. MobileMoE-L reaches 4.71 GB peak RSS at 8K input; its INT4 weights are 2.75 GB. Dummy prompts report lower RSS than real prompts. The official model repo is pinned at `4decae01abfeaf46046b8774fdc4404b3e33a3a4`; model/config downloads were access-restricted, and the license is FAIR Noncommercial Research License dated 21 August 2026. The actual custom operator source was not located. Do not claim its Python code was audited or its runtime reproduced.

### BigMoMo

BigMoMo shares expert loads across a speculative verification window. It uses acceptance-weighted branch selection and a routing-impact-per-movement-cost heuristic for which experts to retain; removed expert probability is reassigned. Section 4.2 explicitly describes approximate target computation. Its co-loading hypergraphs schedule background flash swaps, while latency-critical reads take priority. The paper's pipeline uses mapped-buffer admission, tiled VTCM transfer, HVX dequantization and HMX execution with double buffering. Its evaluations include Q4_0 targets such as Qwen3-30B-A3B with a Qwen3-0.6B draft on Snapdragon 8 Gen 3/8 Elite/8 Elite Gen 5 phones, 12–24 GB memory, and UFS 4.0/4.1. These hardware features and routing relaxations do not transfer as exact CPU methods on Snapdragon 665. No author runtime was found, so sampler details, state rollback, relocation crash safety and actual buffer accounting remain unknown.

### FlashMoE

FlashMoE decomposes experts into layer/expert `.pt` objects, batches expert work during prefill, and keeps per-layer VRAM caches for decode. A three-layer hidden-size-128 SiLU network predicts eviction distance from recency/frequency, trained using Belady-derived targets. The method changes eviction rather than router top-k. The reported platform is Ryzen 9600X, RTX 5070 Ti 16 GB, SK hynix P51 SSD, 64 GB DDR5 and Ubuntu/PyTorch/CUDA, with approximately 1 GB host memory free. It evaluates OLMoE-1B-7B and Qwen3-30B-A3B; the exact quantization is not identified in the reviewed text. The similarly named [EfficientMoE/FlashMoE](https://github.com/EfficientMoE/FlashMoE) repository was empty when checked and was not linked from the paper. [osayamenja/FlashMoE](https://github.com/osayamenja/FlashMoE) and [flash-algo/flash-moe](https://github.com/flash-algo/flash-moe) describe different distributed-GPU or fine-grained-routing systems. Their code cannot substantiate Kim et al.'s SSD cache or learned predictor. No author-linked implementation was verified in this review.

### Paging the Experts and Routide

The paper's checkpoint is MLX affine INT4, group 64, `mlx-community/Qwen3.6-35B-A3B-4bit` revision `38740b847e4cb78f352aba30aa41c76e08e6eb46`, not the target GGUF Q4_K_M. Its graph has 40 layers, 256 experts per layer, top 8, and full/recurrent attention. iPhone 17 Pro Max results span OS/runtime cohorts. Frozen-route replay reports 0% LRU demand hits at 512 MiB, 18.80% seeded-random hits at 512 MiB, and 38.58% LRU hits at 576 MiB. These values describe recorded traces and cache accounting, not universal thresholds or measured physical I/O. Same-runtime Mac tests preserve 2,560 tokens across cache/prefetch settings; full resident-Python versus phone output disagrees in all five compared cases. The paper does not establish cross-runtime parity or prefetch energy savings. The mobile test's sampled peak and thermal stop remain distinct observations.

Routide is the directly linked public implementation, inspected at `d9c1df0dbfa395433abd5c715c8b0dbdea87e9bc`. Its packer rearranges SafeTensors expert slices into aligned expert blocks but does not numerically requantize. One `ExpertCache` is shared by the full `PagedQwenModel`. `ExpertPackReader` validates geometry and can hash-check; hashes are optional by default. The runtime computes its actual route, then `withExperts` pins every demanded expert. Demand joins an in-flight prefetch when possible. Cache insertion occurs after load; only unpinned entries are evicted. An expert larger than capacity or unable to fit around the pinned set bypasses residency but still executes. `PagedExpertKernel` forces MLX evaluation while the lease is held. These are useful lifetime and correctness patterns. Routide is MIT licensed, with copyright notices for ml-explore (2024) and Musa Shams (2026); any copied implementation must preserve its LICENSE and NOTICE requirements. See the pinned [Routide LICENSE](https://github.com/MusaShams/Routide/blob/d9c1df0dbfa395433abd5c715c8b0dbdea87e9bc/LICENSE).

Native replacement options here are LRU and a simple frequency/age hybrid. FIFO, LFU, random and oracle variants are offline replay tools, not all native policies. Its previous-top-one predictor is same-layer temporal prediction: the current layer's actual top expert supplies a hint for the next visit to that layer. Attention wrappers launch the hint before attention, then either wait before MoE or continue with a nonblocking task. The real router remains authoritative; a wrong prediction falls back to demand. Prefetch errors are swallowed at hint time, and later demand retries or reports its own failure. This is prefetch, not draft decoding or cross-layer prediction. Reset waits for layer prefetch tasks, but its detached positional-read loop has no cancellation check; cancelling the caller alone does not stop I/O. Demand and teardown still require a drain contract.

The cache byte counter covers packed expert payload entries, not detached read data, decoded arrays, in-flight tasks, bypassed experts retained by an operation, metadata, shared weights, attention/recurrent state, allocator slack, or OS cache. `Data.subdata` occurs before MLX array creation, so overlapping representations are possible. That does not quantify actual physical copies or allocator retention. The cap therefore does not establish a process memory cap. Prefetch may also refresh LRU state or alter hybrid scores even when a hint hits resident memory. Measure useful and wasted bytes, demand joins, recency changes and total stalls, not prediction accuracy alone.

### Apple's "LLM in a flash"

The paper groups predicted active FFN neurons, stores up-row/down-column bundles, and reuses compact buffers by replacing removed rows with tail rows. That is neuron sparsity, not native MoE routing. Predictors can omit active neurons; Falcon/Phi use ReLU adaptation and Llama 2 uses a FATReLU-sparsified checkpoint. It is not exact inference of an arbitrary original model. Experiments mainly use Mac M1 Max/macOS and custom Metal/MLX-derived kernels; its 16-bit OPT result does not describe a phone Q4_K_M model. Appendix F leaves needed phone kernels outside scope, and Appendix D reports that naive coactivation bundling can worsen reads through duplicate popular neurons. [Apple's author publication page](https://machinelearning.apple.com/research/efficient-large-language) links the paper, but no end-to-end runtime source was identified.

## BigMoe author results and our measurements

BigMoe's README claims Qwen3-30B-A3B, an 18.5 GB file, on a 12 GB Android phone at 5.2 tok/s. Its benchmark chapter describes Q4_K_M, 128 experts, native top 8, 48 layers, four CPU threads, greedy decoding, Android 16 and UFS 4.x. The device is described only as Snapdragon-class, with no exact reproducible SKU. The general benchmark environment records NDK r29 and `armv8.2-a+dotprod+i8mm+fp16`; these are not the ISA features reported by our target probe, and that general environment does not independently bind the later winning row. The committed author log gives 256 generated tokens, 5.234 tok/s, 34 prompt tokens, 6.098 s prefill, 12.996 s load, 19.093 s TTFT, 224.57 MiB application-read window bytes per generated token, 76.5% cache hits, 3,997.9 MiB resident expert payload under a 4,000 MiB cap, and 0.058 s/token overlap stall. A sibling metrics file reports peak RSS 6,287,500 kB and available-memory floor 2,470,856 kB; summary reports 71.8 C. These are committed author records, not independent measurements.

The headline excludes load and prefill. The raw CSV has per-step timings but lacks a model/engine hash preamble and token-ID trace. The general environment records engine `f3371aa`, but does not bind that exact hash to the later winning row. The Qwen3-30B artifact, Android 16 phone, memory class, storage, CPU and historical backend do not match our Qwen3.6-35B GGUF and Android 12 Snapdragon 665. This number demonstrates that one author obtained that result in that setup. It is not a prediction for the target or a performance target.

The author's additional measurements reveal useful failure cases. A contiguous expert-major sidecar improved isolated bandwidth but lost decode throughput against projection-major overlap because it delayed the first projection. A layer-LFU policy improved hit rate but ran about 30% slower amid dense-memory fault pressure. Temporal and stale-gate prefetch increased their own hit/precision counters yet lost overall throughput when storage was already saturated. Turning cache off with overlap regressed a Qwen row from 1.71 to 1.27 tok/s. Cooler later sessions yielded higher throughput without code changes. These results justify measuring consumption order, memory faults, bandwidth slack and thermal state. They do not prove that sidecars, LFU, prefetch, overlap or caches are universally harmful.

The local current API characterization has `evidence/api/phone-35b-direct/run.json`: JSON `Hello!` took 246.767174 s for 24 prompt and 2 completion tokens; SSE-4 took 284.021916 s for 26 prompt and 1 completion token, with normal stop/DONE. Readiness was observed 1,732.275319 s after monitoring started. These are whole API/request observations, not decode tok/s. The run has 4 threads, context 512, 64 slots and a 256 MiB arena allowance. It records lifetime peak RSS 2,191,548 KiB, arena 37,748,736 B, 16,307,453,952 application bytes over 27,648 reads, and zero hits across 1,200 materializer calls. Kernel `read_bytes` 52,384,239,616 and `rchar` 36,749,590,034 are process-lifetime counters with broader scope and cannot be subtracted from run-local application counters to derive amplification.

An older harness aggregate reports about 0.37–0.69 tok/s for longer outputs, but that throughput definition cannot be divided into the current API wall time. No full-resident reference parity exists for all 35B output. API token IDs are unavailable, so plausible response text is not parity evidence. The current 1,024-slot versus 64-slot cache comparison is one consecutive, uncontrolled pair: the larger arena used fewer application bytes but generated more slowly. It warrants controlled investigation of lookup, eviction and materialization overhead. It does not reject cache policy generally. The calculated no-reuse top-8 routed payload is 566,231,040 B (about 540 MiB) per full 40-layer decode, assuming every routed projection is consumed once; this is artifact-based arithmetic, not observed I/O and excludes prefill, metadata, overreads and cache effects.

Strict startup hashing is part of the project's current artifact contract. Current `Artifact` reads the enrolled file through one retained read-only descriptor and computes SHA256 in 4 MiB sequential reads, then rechecks inode metadata and parses GGUF. Its recheck is metadata checking, not content authentication against later mutation. The scalar SHA path is in `src/common/sha256.cpp`; the probe reports SHA2 support, so a dispatched ARMv8 SHA2 implementation with scalar fallback is a testable optimization. But 1,732 s readiness is not an isolated hash timer. No precise startup or decode speed prediction can be assigned to a hash change, `-O3`, or any external result.

Historical evidence issue `R-LOCAL-001` remains open. `evidence/unit3-hash-host.json:17` contains literal unescaped TAB bytes, so standard JSON parsing fails with `JSONDecodeError: Invalid control character`. `bench/hash_diagnostic.cpp:112-134` inserts `path` and `cpu_flags` directly into JSON and can exit successfully after a short read because it breaks on nonpositive read without checking that requested bytes were completed. Do not silently repair the historical record or parse it permissively and call it valid. Fix the emitter and short-read check in a separate implementation unit, then collect new evidence. Existing historical numbers can be labeled as such with the validation defect disclosed.

## Current llama.cpp flags and the present engine boundary

The supplied Android guide URL is a build guide, not a flash-to-CPU MoE streaming design. In the independently inspected current upstream pin `1ba568c5ad5c6c718984bd2bf4e7c71485b706f9`, `--cpu-moe` and `--n-cpu-moe` control CPU placement. `--moe-cache-mib` is a GPU cache for CPU-hosted expert weights. The `llama-moe-cache.cpp` implementation has grouped segmented-LRU and protects selected IDs, but its constructor requires GPU/IGPU and host expert storage. It is not a bounded flash-to-CPU cache on this CPU-only path. Current `load_mode` options include mmap, mlock, direct I/O, and `lazy_mode` for on-demand row access to certain tensors. These concepts do not replace explicit selected-expert storage; the options have evolved since our production pin. New upstream `DirectIO` uses a bounded aligned buffer and copies requested bytes. Its padding and bounce-buffer costs count, and no target filesystem result shows it wins on this phone.

The local engine's boundary is explicit. `src/backend/artifact.cpp` validates the enrolled artifact and GGUF index. `src/backend/moe_stream.cpp` binds the proposal to actual consumer tensors, reads actual routed IDs, deduplicates, rejects a union beyond slot/lease limits, obtains cache leases, and builds compact descriptors that remap the native IDs. Every selected expert remains present. The current size-class stores persist per expert byte-size class, with shared finite arenas and `(table_id, expert)` keys. They are not destroyed at every tensor switch; that statement describes earlier history. Zero hits reflect this observed workload/capacity, not proof that the store cannot retain entries.

`src/residency/store.cpp` pins hits, reserves free or LRU unpinned slots, reads misses serially, rolls back on cancellation/error, and returns a lease. Its victim selection scans the slot array for each miss, so it has O(slot_count * misses) selection work. BigMoe uses linked LRU metadata. The local selection overhead is an optimization hypothesis to profile, not a demonstrated cause of the historical read-time increase. `file_source.cpp` bounds reads to 1 MiB chunks and handles EINTR, EOF, and cancellation. `read_calls` counts successful whole-entry loads, not raw pread syscalls. The staged patch materializes the full routed union on thread 0 and then releases workers through a barrier. It bypasses `ggml_compute_forward_mul_mat_id_tiled` because that implementation reads `dst->src[0]` rather than the staged descriptors. The vector-dot kernel still runs quantized arithmetic. How much the tiled exclusion costs on the phone is unmeasured.

The staged compact representation and BigMoe's canonical expert offsets are concrete alternative designs. The first minimizes arena bytes and remaps IDs; the second preserves native expert addresses and can make upstream indexed kernels consume the original layout. Canonical backing adds sparse virtual reservations, page tables, commitment rounding, tail slack and a difficult eviction/readiness lifetime. Neither design wins by inspection. Compare them on the same artifact, native routing, CPU kernel, quantized slices and prompt schedule. Keep backend graph, tokenizer, routing, attention, recurrent state, and numerical kernels with the pinned backend unless a source-backed integration gate proves a change necessary.

## Findings from optimization families

Several apparent "speedups" in the literature actually combine model transformation, changed routing, different precision, heterogeneous execution, or different measurement units. PowerInfer-2's hot-neuron execution, MobileMoE's new architecture, Apple's neuron omission, and BigMoMo's approximate expert removal cannot be credited as exact streaming gains. EdgeMoE's mixed expert precision and FP32 expansion changes bytes even though its prefetch misses recover actual router choices. FlashMoE's learned eviction is closer to an exact storage policy but its GPU/VRAM system, `.pt` layout and absent source block transfer. Paging/Routide has the cleanest public exact-demand and lease patterns but uses different quantization, MLX arrays, and memory accounting that omits important process costs.

Learned eviction is separable from learned routing. Offline trace training can propose a victim policy without changing selected experts. It still needs held-out prompt domains, a predictor-cost budget, metadata memory accounting, and a demonstrated improvement over simple LRU/SLRU/hybrid on the target CPU. An oracle policy is only an offline upper bound. Trace hit rate is not device throughput. Seeded-random can outperform LRU on a particular frozen route as the Paging paper reports; that is a prompt-trace observation, not a reason to ship random eviction.

Cache and prefetch metadata are part of the experiment. A cache hit can refresh recency and alter the next victim; preserving recency can alter a hybrid score. A large cache consumes memory and may displace useful dense weights or trigger faults. A prediction can be accurate yet lose if it competes with demand for saturated storage bandwidth. Prefetch must remain lower priority than demand, carry bounded bytes and tasks, cancel or drain safely, and never make a selected expert optional.

Batching and prefix reuse also affect storage. The current planner admits prefill width conservatively: for 64 slots and top 8, the admitted microbatch is 8, while context 512 is not batch 512. A future capacity rule based on `min(expert_count, tokens * topk)` might permit larger batches, but it is not the current proof and requires implementation, memory reservation and numerical/state checks. Prefix snapshots for the hybrid attention/recurrent model must bind token IDs, model/template identity, positions and recurrent state, not merely KV bytes. Old and new snapshots coexist during replacement. A cache persisting across requests does not mean logical model state can persist across them.

## Concrete experiment order

1. **Make measurements interpretable.** Repair the evidence emitter and short-read defect in a separate change. Keep historical invalid JSON untouched. Capture startup hash, GGUF parsing/binding, context allocation, prefill, first token, decode, CPU time, source wait, conversion/packing, useful bytes, application-read bytes, and system physical I/O separately. Record token IDs and teacher-forced logits on fixtures. Compare repeated cool/warm runs with thermal and cache state recorded. The existing API wall times cannot identify the dominant stage.
2. **Optimize startup as its own stage.** Benchmark read-only artifact open, hash-only, and combined validation; preserve the current digest and failure semantics. Test runtime SHA2 dispatch versus scalar fallback using standard vectors plus bitflip/truncation cases. Treat compiler optimization level as a controlled hypothesis. Do not replace integrity with path/mtime caching absent a new artifact contract.
3. **Compare materializers synchronously first.** Keep compact size-class arenas and prototype canonical sparse backing behind a source gate. Compare native top-k, gate/up/down and fused variants, Q4_K/Q6_K, batch sizes, dirty reuse and consumer lifetime. Check exact selected byte slices and logits/token IDs. Account page tables, rounded commitment, tail slack and simultaneous staging. The current compact staging path excludes tiled `mul_mat_id`; a separately gated tiled-aware version is a specific candidate.
4. **Measure reads before adding overlap.** Use actual expert traces and extent sizes to compare buffered reads, verified aligned direct I/O, sorted/coalesced offsets and one, two, or four bounded workers. Vary one factor per arm. Track useful/read/physical bytes, overread, demand stalls, queue wait, CPU time and total generation time. `preadv` does not gather arbitrary offsets. Do not infer a storage win from a sequential bandwidth ceiling.
5. **Study cache policy under equal byte budgets.** Replay actual prompts and compare current global size-class LRU, SLRU, frequency/layer-distance, per-layer reserves, hot anchors and seeded random. Use oracle only as a bound. Include lookup/eviction CPU cost, working-set knees, domain shift, cold/warm runs, repeated turns and current demand pins. This responds to both the single uncontrolled local cache pair and BigMoe's negative layer-LFU result without treating either as universal.
6. **Add readiness overlap only after kernel gates.** Define generation-tagged Empty, Loading, Ready, Failed and Cancelled states. A consumer must wait for its exact buffer generation and cannot read a partial projection or evict a pin. Preserve gate/up/down consumption order; filling a complete bundle late can block the first projection. Inject delayed reads, EOF, I/O failure, cancellation during chunks, compute failure and teardown. Drain consumers before release. Require hook availability in the tested mode instead of silently disabling overlap. Compare logits and token IDs to the serial path.
7. **Test graph width and request reuse separately.** Sweep admitted prefill widths under the same artifact and correctness controls, recording compute/KV/recurrent reservation and prefill time. Then test exact prefix snapshots across repeated prompts, cancellation, interruption and reopen. Prove full hybrid state restore and invalidation, and count old/new snapshot overlap. Smaller graph reservations may free cache memory; larger batches may increase expert union.
8. **Defer sidecars and predictors until traces justify them.** If a sidecar wins in trace analysis, bind it to source digest, schema, quantization, dimensions, companions, padding and per-extent hashes. Write atomically and preflight temporary double-storage. Preserve GGUF quantization and aliases. Compare projection-major versus expert-major with first-consumer readiness; BigMoe's sidecar result shows read order can outweigh isolated throughput. Only then try demand-priority, cancellable exact prefetch with useful/wasted-byte and cache-pollution accounting.
9. **Treat n-gram/MTP decoding as a separate project phase.** Include draft memory and compute, expert union across candidates, acceptance, recurrent/KV rollback, rejected branch reclamation and target latency. Report accepted tokens per target invocation and target bytes per accepted token. Greedy sequence parity is narrower than stochastic distribution equivalence. Do not combine any result with expert pruning.

A CPU characterization of the pinned BigMoe implementation on the same actual 35B GGUF is a useful early comparison beside the current engine. Keep the current engine as the production baseline; the external run is a research comparison, not a second production backend or a phone speed claim. Use native top 8 and the same prompts, context, thread count, timing boundaries, and correctness evidence. Start cache admission from refreshed memory and a complete reservation, not the author's 4,000 MiB setting. Exclude reduced top-k, dropping, substitution, and route-ahead. Record exact repository and backend hashes, model hash, command, hardware, thermal state, output token IDs, source wait, all memory categories, and whether load and prefill are included. The paper audit does not provide a verified command line for this target, so derive a command from the pinned source and its own documented CLI rather than guessing flags. Do not use the author's old benchmark row as a substitute.

## Open gaps and decisions

| Gap | What remains unknown | Consequence |
|---|---|---|
| Full 35B parity | No resident-reference token-ID and full-logit comparison for the current artifact | Correctness gate is open; plausible API text does not close it. |
| Memory cap | Existing counters do not cover every backend, OS and transient allocation | No hard-cap claim until reservations include all live representations and are checked at admission. |
| Startup/readiness | 1,732 s is elapsed readiness, not an isolated SHA timer | Do not attribute startup to hashing without stage timing. |
| Cache pair | One uncontrolled 1,024 versus 64 slot comparison | Repeat controlled arms before changing the policy conclusion. |
| R-LOCAL-001 | Invalid historical JSON and possible short-read success in the diagnostic emitter | Preserve old file; repair emitter and collect new records separately. |
| R-PAPER-001 | BigMoMo v2 abstract gives 1.82x over its best speculative baseline while Section 5.2 gives 1.76x over its best baseline; aggregation not reconciled | Keep both scopes and values, rather than selecting the more favorable headline. |
| BigMoe release provenance | Historical Qwen benchmark lacks a bound engine/model hash and token IDs | Treat 5.234 tok/s as author evidence only, not a reproducible target. |
| External code gates | BigMoMo, FlashMoE, EdgeMoE, PowerInfer-2 and Apple runtime gaps; MobileMoE source restricted | Do not invent source APIs or claim line-level audits/reproduction. |
| Recurrent/prefix reset | Failure and cancellation paths not fully fault-injected for every hybrid architecture | Prove state rollback/reopen separately before reuse or speculation. |
| Android accelerator | QNN examples require modern packages/targets; no target-specific proof | Keep CPU path; no inference from a Snapdragon/Hexagon brand name. |
| File transfer and sidecar | Current available-storage snapshot is stale; sidecar needs temporary extra space | Refresh actual free space and preflight before any large transfer or conversion. |

No production-backend switch follows from this review. BigMoe's small fork is an experiment candidate after the phase gates, not an approved integration. Stock llama.cpp placement, mmap, lazy rows, or GPU cache options do not constitute the required expert streamer. The present CPU path is the baseline to improve and preserve.
